# 要件定義書 (Requirements Definition)

プロダクト「防災体験VR（仮称）」の目的・対象ユーザー・スコープを定める．
大会の日程・審査基準は [PLAN_01](PLAN_01_大会概要とスケジュール.md)・[PLAN_03](PLAN_03_審査基準とアワード.md) を参照する．

※ 2026-10-24 に方向性を「地震の体験（家・電車・エレベーター）」から「**小学校の火災避難訓練シミュレーション**」に変更した．地震シナリオは要件から外し，コードは当面残す（共通部分を流用しつつ，新しい仕様の実装に合わせて整理する）．

## 目的 (Purpose)

- 学校の避難訓練は，火元も避難経路も毎回ほぼ同じで，「放送どおりに並んで歩く」ことが中心になりがちである．火元によって逃げ道が変わることや，煙の中での動き方を，自分の体で試す機会が少ない
- 教員が**自分の学校**の校舎を簡単に再現し，**火元を自由に変えて**避難訓練の場面を作れるようにする
- 生徒はスマホと簡易 VR ゴーグルで，その場面の中を実際に歩いて避難する．没入感のある環境で，自分の学校での避難経路と煙への対策を体で覚える

## 対象ユーザー (Target Users)

| 区分 | 想定 | 使う画面 |
| --- | --- | --- |
| 教員 | 小学校の教員（防災担当・担任）．3D の知識は無い | PC のブラウザで校舎の作成・火元の設定・正解経路の確認を行う．体験中は見守り画面で生徒の目線を見る |
| 生徒 | 小学生．学校が用意したゴーグルとスマホを 1 人 1 台使い，各自が独立した VR 空間で体験する（空間は共有しない） | スマホ＋ゴーグル |
| デモの体験者 | 審査員・来場者（初めて使う人が説明なしで 2〜3 分体験できること） | 同上 |

## 利用の流れ (Usage Flow)

```text
【教員・PC】
校舎を作る（図面の写真を下敷きにパーツを置く）
→ 火元・防火シャッター・生徒の開始地点（教室）・集合場所を置く
→ システムが正解の避難経路を提案し，教員が修正する
→ モード（学習／テスト）を選び，QR コードを表示する
→ （任意）「見守り画面を開く」で見守り画面を開き，体験中の生徒の目線を PC やプロジェクタで見る

【生徒・スマホ＋ゴーグル】
QR コードを読み取る → 開始画面（許可の取得）→ キャリブレーション
→ VR で避難する → 結果画面
```

## 利用機材 (Hardware)

| 機材 | 内容 |
| --- | --- |
| VR ゴーグル | ELECOM VRG-S01BK（4.0〜6.5 インチのスマホ対応，バンド固定式，ボタン・コントローラーなし，目幅調整あり，ピント調整なし）．学校が複数台を用意する想定 |
| スマホ | デモは **iPhone**．Android でも動くようにする |
| 背面カメラ | ゴーグル装着時も外が見えることを確認済み（ハンドトラッキングに使う） |
| 教員の端末 | PC のブラウザ（エディタ・見守り画面用） |

- ゴーグルにボタンが無いため，**生徒の操作はすべて体の動きと手で行う**（画面タッチは開始前の許可取得だけ）

## 機能要件 (Functional Requirements)

### 教員側: 校舎エディタ (Editor)

#### 必須 (Must)

| ID | 機能 | 内容 |
| --- | --- | --- |
| E1 | 図面の下敷き | 校舎の図面の写真を読み込み，半透明の下敷きとして表示する．位置・大きさ・回転を合わせられる |
| E2 | パーツの配置 | マス目の上に，事前に用意したパーツ（教室・廊下・壁・ドア・出口（昇降口）・防火シャッター）を置いて校舎を作る．3D の校舎はマス目から自動で組み立てる |
| E3 | 訓練条件の設定 | 火元・生徒の開始地点（教室）・集合場所（屋外）を置く |
| E4 | 延焼の自動計算 | 火元から時間とともにマス目上で火と煙が広がる．防火シャッターで延焼が止まる．教員は広がり方をプレビューで確かめられる |
| E5 | 正解経路の提案と修正 | 延焼を考慮して火と煙を避けた最短の避難経路をシステムが提案し，教員が学校の決まり（使う出口等）に合わせて修正する |
| E6 | モードの選択と共有 | 学習モード／テストモードを選び，校舎・訓練条件・正解経路を埋め込んだ URL と QR コードを表示する |

#### できれば (Should)

| ID | 機能 | 内容 |
| --- | --- | --- |
| ES1 | 延焼箇所の手動追加 | 自動計算に加えて，燃え広がる箇所を教員が手で足せる |
| ES2 | 複数フロア | 階段のパーツを追加し，2 階以上の校舎を作れる．まず 1 フロアで動作を確かめてから広げる |
| ES3 | 図面の自動読み取り | 図面の写真から AI でマス目の下書きを自動で作り，教員が手で直す．避難訓練の体験がひととおり作れた後に，実現できるかを検証する |
| ES4 | 開始地点ごとの QR | 教室ごとに別の QR コードを出し，クラス単位の訓練に使えるようにする |

### 生徒側: VR 避難体験 (VR Experience)

#### 必須 (Must)

| ID | 機能 | 内容 |
| --- | --- | --- |
| F1 | VR 表示 | 左右 2 画面の立体表示．頭の向きに合わせて視点が回る |
| F2 | 足踏み歩行 | その場で足踏みすると視線の方向へ前進する |
| F3 | しゃがみ | しゃがむと視点が下がり，しゃがんでいる間は低い姿勢として扱う．**現行の判定方法は改善が必要**（後述「技術的な課題」） |
| F4 | 火と煙 | 教員の設定どおりに火と煙が時間とともに広がる．煙は天井近くほど濃く視界を悪くし，**しゃがむと視界が晴れる** |
| F5 | 音声・音響 | 非常ベル・校内放送（火元の場所を伝える）・炎の音で臨場感を高める．**音声認識（声での操作）は行わない** |
| F6 | 学習モード | 正解の避難経路を VR 空間の床に表示し，それに沿って避難する |
| F7 | テストモード | 経路を表示せずに避難し，結果画面で正解経路と比べる．**学習モードを先に完成させてから作る** |
| F8 | 結果表示 | 体験後に，地図の上に自分の経路と正解経路を重ねて示し，次の 3 つを評価する |

F8 の評価項目:

| 評価項目 | 内容 |
| --- | --- |
| 経路 | 正解経路から外れた箇所・火や煙に近づいた箇所を地図に示す |
| 煙の中での姿勢 | 煙の濃い場所で低い姿勢（しゃがみ）をとれていたか |
| 避難時間 | 非常ベルから集合場所に着くまでの秒数 |

体験中の評価（エラー行動の赤い表示）:

- 行動の評価は，体験の後だけでなく **体験中にその場で示す**．エラー行動（避難として誤った行動）をしている間，**VR の画面を赤く表示** し，これを評価とする（体験者にも，デモで横から見ている人にも，誤った行動がすぐ分かるようにするため）
- エラー行動の示し方は赤い表示に統一し，エラー行動を新しく足す時も同じ表示を使う
- 赤い表示はエラー行動をしている間だけ出し，やめたら消す．強く点滅させない（非機能要件の「安全」）
- 現在のエラー行動は「煙の中で立っている（低い姿勢をとっていない）」とする．もとからある「火に近づいた時の警告」も同じ赤い表示を使う．エラー行動の一覧・判定のしきい値・赤い表示の見た目は仕様設計（`docs/04_SPEC/`）で決める
- 結果画面（F8）は振り返りとして残し，赤い表示が出た箇所を地図に示す

#### できれば (Should)

| ID | 機能 | 内容 |
| --- | --- | --- |
| S1 | キャリブレーション | 体験開始時に立ち姿勢・しゃがみ姿勢・足踏みを 1 回ずつ行い，判定のしきい値を本人に合わせる |
| S2 | 観客向け表示（見守り） | 体験者が見ている目線を PC やプロジェクタに映す（デモで観客に体験内容を伝えるため．後で，教員が体験中の生徒を見守るためにも使う）．映像は送らず，生徒のスマホから位置・頭の向き・姿勢などの状態と，ロビーの指示の文・避難の記録だけを送り，PC で同じロビー・校舎・結果画面をもう一度描く．付け足しの機能で，届かなくても体験は変わらない（後述「非機能要件」の「通信」）．**1 人の目線を映す最小限（見守りの段階 1）は，デモに要るため Must と同じく先に作る**．複数の生徒の見守り等（見守りの段階 2）は後で足す．仕様は SPEC_01「見守り」 |
| S3 | 立体音響 | 頭の向きに合わせて音の聞こえる方向が変わり，火元の位置が音で分かる |
| S4 | 防火シャッターのくぐり戸 | 閉じたシャッターのくぐり戸を手で押して開けて通る（ハンドトラッキング） |

S2（見守り）の段階（後述「開発の順序」の段階とは別の数え方）:

| 見守りの段階 | 内容 | 優先度 |
| --- | --- | --- |
| 段階 1（デモの最小限） | 体験者 1 人のロビー（キャリブレーション）と避難の目線，煙の中で立つ等の赤い表示，終わった後の結果画面を，前もって開いておいた PC の見守り画面に，手で操作せずに映す（観客が見るものを，ゴーグルの人が見ている画面と同じにする）．終わっても・もう一度体験しても開き直さない．エディタの QR に見守りの部屋の ID を入れ，エディタから見守り画面を開ける（URL を手で直さない）．生徒の端末と同じ音（避難中の効果音・ナレーション，ロビーのナレーション）を，どの音を鳴らすかの合図だけを送って PC のスピーカーから鳴らす（観客にも同じ音を聞かせる．ブラウザの自動再生の制限のため，見守り画面を開いた後に 1 回クリックする） | Must 寄り（発表の前に完成させる） |
| 段階 2（後で足す） | 複数の生徒（地図の点と名前・選び直し），見守り画面の URL を文字でも出す，接続待ちの QR，つなぎ直した時のドアの送り直し，情報の表示，生徒の名前の入れ方，中継の上限の数 等（一覧は SPEC_01「段階 2: 後で足すもの」） | Should |

### やらないこと (Out of Scope)

- 地震シナリオ（家・電車・エレベーター）．コードは当面残すが要件からは外す
- サーバーでの保存・ユーザー登録・ログイン・体験履歴の保存（見守り（S2）の中継は，届いたものを流すだけで保存しないため，これに当たらない）
- クラス全体の結果の集計（結果を保存するサーバーが必要なため．見守りは体験中の様子を見るだけで，結果を集めない）
- 複数人が同じ VR 空間に入ること（1 人 1 台で各自が独立に体験する）
- ゴーグルを使わないタブレット向けの 1 画面モード
- 専用 VR 機器（Meta Quest 等）やネイティブアプリへの対応
- 初期消火（消火器を使う等）
- 口をハンカチで覆う動作の判定（背面カメラに写らないため，ナレーションで促すだけにする）

※ 時間が余った時や Hack Day 後の追加開発で取り組む案は [PLAN_05 追加機能の候補](PLAN_05_追加機能の候補.md) にまとめる．

## 開発の順序 (Development Order)

デモで動くものを早く作り，そこから広げる．

| 段階 | 内容 | 主な ID |
| --- | --- | --- |
| 1 | 1 フロアの校舎をエディタで作り，学習モードで避難できる（火・煙・正解経路の表示・結果表示） | E1〜E6，F1〜F6，F8 |
| 2 | テストモード | F7 |
| 3 | 複数フロア（階段） | ES2 |
| 4 | 図面の自動読み取りの検証 | ES3 |

- S2 のうち「見守りの段階 1」（デモの最小限）は，発表で体験者の目線を映すために，上の表の 1 と並べて発表の前に完成させる．「見守りの段階 2」は，上の表の 2 以降と同じ時期に回す

## 体験の流れ (Experience Flow)

1 回の体験は 2〜3 分とする．

```text
開始画面（QR から開く．許可の取得）→ キャリブレーション
→ ① 授業中の教室 → ② 非常ベルと校内放送 → ③ 避難 → 集合場所に着く（終了）→ 結果画面
```

| 段階 | 起きること | 求める行動 |
| --- | --- | --- |
| ① 授業中の教室（10 秒程度） | 教員が指定した教室から始まる．ナレーションで状況を伝える | 周りを見回す |
| ② 非常ベルと校内放送 | 非常ベルが鳴り，校内放送で火元の場所を伝える | 放送を聞き，逃げる方向を判断する |
| ③ 避難 | 火と煙が時間とともに広がる．学習モードでは床に正解経路が表示される | 火と煙を避けて集合場所まで歩く（F2）．煙の中では低い姿勢をとる（F3） |
| 終了 | 屋外の集合場所に着いたら終わる | — |

- 制限時間を設け，過ぎたら「逃げ遅れ」として打ち切り，結果画面へ進む（体験が止まらないようにする）
- 火のマスには入れないようにし，近づいたら警告する．近づいたことは結果画面の経路に示す
- 視点（カメラ）を大きく揺らさない（VR 酔いを防ぐ．非機能要件の「安全」）
- 各段階の秒数・ナレーションの文面・判定のしきい値等の詳細は仕様設計（`docs/04_SPEC/`）で決める

## 非機能要件 (Non-functional Requirements)

| 項目 | 要件 |
| --- | --- |
| 対応環境 | 生徒側は iPhone の Safari を最優先とし，Android の Chrome でも動くこと．教員側は PC のブラウザ（Chrome）で動くこと |
| 配布 | URL を開く・QR コードを読むだけで使える（アプリのインストール不要） |
| データの受け渡し | 校舎・訓練条件・正解経路は URL に埋め込んで渡す．サーバーには校舎や生徒のデータを保存しない（見守りの中継も，届いたものを流すだけで保存しない） |
| 描画性能 | iPhone で 30 fps 以上を保つ（VR 酔いを防ぐ） |
| 体験時間 | 1 回 2〜3 分（デモの持ち時間と酔いを考慮） |
| 安全 | 体験前に周囲の安全確認を促す．急な視点移動・強い点滅を避ける |
| 通信 | 体験は通信が無くても最初から最後まで動く（会場の回線が不安定でもデモできる）．見守りのための通信は任意の付け足しとし，つながらない・途中で切れる・遅れる時も体験に影響しない．見守りで送るのは状態（1 回 20 バイトほど）と小さな知らせ（ロビーの指示の文・避難の記録．1 回 4 KiB まで）だけで，映像は送らない（スマホを重くしない） |
| 登録 | ログイン・ユーザー登録は要らない（見守りも，生徒と見守り画面の URL に入れた部屋の ID だけでつながる） |

## 技術的な課題 (Technical Challenges)

- **URL に載るデータ量**: QR コードで読み取れる長さには限りがある．マス目のデータを圧縮して埋め込む．複数フロアに広げた時に収まるかを確かめる
- **マス目からの 3D の組み立て**: 壁・ドア・シャッターを隣のマスとの関係から自動で置く．パーツの見た目は事前に作っておく
- **延焼と正解経路の関係**: 火と煙は時間とともに広がるため，正解経路は「その時刻に通れるか」を考慮して求める必要がある
- **煙の描画負荷**: 煙の表現（フォグ・パーティクル）と手の認識を iPhone で同時に動かすと重い．負荷の軽い表現から始める
- **しゃがみ判定の精度**: スマホの加速度だけでは上下の移動量が積分誤差でずれやすい．開始時のキャリブレーション（S1）や判定方法の見直しが必要
- **iPhone の制約**: iPhone の Safari は WebXR に対応していない．また音声の再生・センサーの利用には最初に 1 回画面をタップしてもらう必要がある．詳細と対策は [ENV_01](../02_ENV/ENV_01_技術スタック.md) に書く
- **歩く距離**: 校舎は部屋より広いため，足踏みでの移動速度を体験時間に収まるよう調整する
- **見守りの通信**: 学校の Wi-Fi は端末どうしの通信を遮断していることが多く，https のページから LAN の中の端末へ直接つなぐこともできない．そのため，データを保存しない中継（Cloudflare Workers + Durable Objects の WebSocket）を通す．仕様は SPEC_01「見守り」

## デモ (Demo)

- デモ用の校舎（チームの大学の建物，または架空の小学校）を事前にエディタで作っておく
- 発表では「火元を変える → 正解経路の提案が変わる → VR で避難する → 結果画面」の順に見せ，教員側と生徒側の両方を伝える
- 避難中は，煙の中で立つと画面が赤くなる様子を観客にも見せ，評価がその場で分かることを伝える
- 見守り画面（S2 の段階 1）をプロジェクタにつないだ PC で前もって開いておき，体験者の目線を観客に見せる．会場の回線で中継につながらない時の代わり（スマホの画面のミラーリング等）は SPEC_01「デモ当日の注意」に書く．どちらでも体験そのものは変わらない

## 審査・スポンサー賞との対応 (Judging Alignment)

- 問題着眼点: 毎回同じ火元・同じ経路になりがちな避難訓練を，「自分の学校」で「火元を変えて」体験できるようにする
- 実行・実現可能性: 安価なゴーグルと Web だけで，教員が自分の学校の訓練を作れる．データを保存するサーバーもログインも要らず導入しやすい（見守りの中継は流すだけ）
- 完成度・動作性: デモで火元を変えて経路が変わる様子と，体験者が歩き・しゃがむ姿を見せる
- 狙えるスポンサー賞（候補）: 三菱重工業（安心・安全．本命），ソフトバンク（学び），ULS コンサルティング（図面の自動読み取りに AI を使う場合）
