# 追加機能の候補 (Feature Backlog)

Hack Day の必須機能（[PLAN_04 要件定義書](PLAN_04_要件定義書.md)）が動いた後，時間が余った時や Hack Day 後の追加開発（Kaizen Sprint 等）で取り組む案をまとめる．
着手するときは，内容を PLAN_04 の機能要件に移すか，Issue（`/task-create`）にする．

出典: チームメンバーによるシステム基本設計の検討メモ（2026-10-24）と，それに対する技術面の検討．

## 各案の検討メモ (Notes)

### AI による振り返り (AI Feedback)

- 送るのは**行動ログ（どの場面で何をしたか・かかった時間等の JSON．数 KB）だけ**にする．録画は送らない
- 生成 AI の API キーはブラウザに置けない（提出リポジトリは public で，配信先の GitHub Pages は静的サイトのため）．キーを持つ小さなサーバー関数（Cloudflare Workers 等）を用意し，ブラウザはそこへログを送る
- 体験中は通信しない方針（PLAN_04 の非機能要件）を保つため，送るのは体験の終了後だけにする．通信できない時は，端末内で作る結果表示（PLAN_04 の F7）だけを出す
- 狙える賞: ULS コンサルティング（AI エージェント），ソフトバンク等（[PLAN_03](PLAN_03_審査基準とアワード.md)）

### 機械学習による動作判定 (ML-based Motion Detection)

- 公開データセット（WISDM・UCI HAR）は，スマホを腰やポケットに付けて実際に歩いた時のデータであり，頭に付けてその場で足踏みする本アプリとは波形が大きく異なる．そのまま流用しても精度は期待しにくい
- まずはルールによる判定（[ENV_01](../02_ENV/ENV_01_技術スタック.md)「歩行・しゃがみ判定」）で作り，開発用ページで記録した**自分たちの足踏み・しゃがみのデータ**を貯めておく．精度が足りない場合に，そのデータで小さなモデル（1D-CNN 等）を学習する
- 推論自体は 1 回数 ms で済む見込みだが，ブラウザで動かすための実行環境（TensorFlow.js・ONNX Runtime Web 等）の読み込みが増える

### 体験結果の Bluesky 投稿 (Share to Bluesky)

- 狙える賞: Bluesky 賞（Award Day のみ．条件: AT プロトコル／Bluesky API を活用した作品．[PLAN_03](PLAN_03_審査基準とアワード.md)）．スポンサー提供物として API が用意されており，質問は Slack `#support-bluesky`
- 最小の形は，結果画面に「Bluesky で共有」ボタンを置き，投稿文（例: 「地震→火災の避難体験で〇点．机の下に隠れられた」）を入れた投稿画面を開くだけ．ログインや API キーの管理がアプリ側に要らない
- AT プロトコルの API で直接投稿する（画像付き投稿・ハッシュタグでの集計等）場合は，ユーザーのログインと認証情報の扱いが要る．秘密情報をブラウザに置かない方針（ENV_01）との兼ね合いを先に決める
- 防災の啓発として「体験したことを周りに広める」流れを作れるので，問題解決の説明（審査基準 1・2）にもつなげやすい

### 体験の録画 (Recording)

- Web では `MediaRecorder` で描画中の画面（canvas）を録画できる
- 立体描画・手の認識と同時に動画の圧縮を行うため，iPhone で 30 fps を保てるかを先に確かめる必要がある
- 録画は端末に一時保存し，送る場合も体験の終了後にまとめて送る（体験中の送信は描画を乱すため）
- 発表用のデモ動画が目的なら，iPhone 標準の画面収録で足りる

### マップエディタ (Map Editor)

自分の家・学校・職場などの間取りをユーザーが作り，その中で避難を体験できるようにする．類似事例は調べた範囲では見つかっていない（[PLAN_06](PLAN_06_類似事例の調査.md)「見取り図から VR 空間を作る事例」）．

#### 今の部屋の作りとの対応

今の部屋はすでにパーツの組み合わせで作られている（[TECH_01](../05_TECH/TECH_01_3D空間の構成.md)）．エディタが出す「間取りの JSON」から部屋・当たり判定・エリアを作る仕組みを 1 つ用意すれば，残りは今のものを使い回せる．

| エディタで置くもの | 今あるもの | 必要な作業 |
| --- | --- | --- |
| 壁（ドア・窓の開口部付き） | `splitWallAroundOpening()` で開口部を除いた壁の板を作り，そのまま当たり判定にしている | 座標を定数ではなくデータから受け取る |
| 家具・がれき | 家具は直方体の当たり判定．高さ 0.05 m 以下はまたげる | がれきも「直方体＋見た目」で同じ仕組みに乗せる |
| ドア | `DoorBlocker` が開いている間だけ通れるようにしている | そのまま使う |
| 避難経路・出口・危険な場所 | エリア（床の XZ の矩形）と，出入りの `areaEntered`／`areaExited` イベント | GUI で引いた経路・出口をエリアに変換する |
| 炎（煙の範囲ではしゃがむ） | しゃがむと目の高さが 0.55 m に下がる | 「煙のエリアの中で目の高さが一定以上」を危険な行動としてシナリオで判定する |
| 評価 | データ駆動のシナリオ（`src/scenario/engine.ts`）と結果画面 | 置いたパーツからシナリオの定義も作る |

#### 作り方の案

- **エディタ**: 2D のマス目に，壁・ドア・窓・家具・がれき・炎・出口・避難経路をタップ／ドラッグで置く（上から見た図．Canvas で足りる）．three.js で上から見下ろす表示にすると，置いた結果をその場で確かめられる
- **避難経路**: マスをなぞる線か，チェックポイントを順に置く形．マス目なので，出口まで本当にたどり着けるかを経路探索（A\*）で自動チェックし，「がれきで道がふさがっている」等の警告を出せる
- **保存**: まずは端末内（localStorage）と JSON ファイルの書き出し・読み込み．サーバーは要らない
- **3D 化**: 壁は線分に高さ・厚みを付けて板にし，開口部は今の関数で除く．家具・がれきは Kenney 等の glTF 素材を置き，当たり判定は直方体にする．炎は見た目（パーティクル）・音・エリア（近づくと危険，煙の範囲ではしゃがむ）を 1 つのパーツにまとめる

#### 注意点

- **スマホの処理負荷**: 左右 2 画面で描くため，パーツの数を抑える．同じパーツをまとめて描く（`InstancedMesh`）・影を減らす・炎のパーティクルを抑える
- **広さ**: 足踏みで進むので部屋の大きさに制限は無いが，広い建物は体験が長くなる．制限時間かマップの大きさの上限を決める
- **使う画面**: ゴーグル装着中は操作できないので，エディタは装着前のスマホか PC の画面で使う．ホームから「マップを作る」に入る形が自然
- **分担**: エディタ・JSON から 3D を作る部分・炎のパーツは触るフォルダを分けられるので並行しやすい

#### 作る順番

1. 間取りの JSON の形を決め，今の部屋をその JSON で書き直して同じ部屋が作れることを確かめる
2. JSON から 3D の部屋・当たり判定・エリアを作る
3. エディタ（壁・ドア・出口・炎・がれき・避難経路）と，たどり着けるかのチェック
4. 炎のパーツと「しゃがむ」判定をシナリオにつなぐ
5. 余裕があれば AI による見取り図の読み取り

※ 1・2 だけでも「データから部屋ができる」という土台が固まる．

### AI による見取り図の読み取り (AI Floor Plan Reading)

- 画像を読める LLM（Claude 等）に見取り図の写真を渡し，マップエディタと**同じ間取りの JSON**（壁の線分・ドア・窓）を出させる．人はそれをエディタで直し，炎・がれきを置くだけにする
- **サーバー関数が要る**: API キーをブラウザに置けないため（「AI による振り返り」と同じ．サーバー関数はまとめて検討する）
- **縮尺**: 写真だけでは実際の寸法がわからない．「この壁は 3.6 m」のように 1 か所だけ人に入力してもらう
- **精度**: きれいな不動産の間取り図ならかなり読めるが，手描きや複雑な図は崩れる．「AI は下書き，人が直す」前提にすれば，エディタがあるので問題にならない
- 見取り図の画像から壁を自動で認識する処理は研究でも長く取り組まれてきた難しい処理のため，AI を使わない代わりの案として「撮影した写真を下絵にして，なぞって壁を引く（半自動）」も用意できる
