# 画面遷移とモジュール構成 (Screen Flow & Module Structure)

「防災体験VR（仮称）」の画面の流れ，モジュールの分け方と担当，モジュール間で受け渡すデータ，シナリオ定義の形式を定める．
要件は [PLAN_04 要件定義書](../03_PLAN/PLAN_04_要件定義書.md)，技術選定は [ENV_01 技術スタック](../02_ENV/ENV_01_技術スタック.md) を参照する．

シナリオ（#9）はまだ決まっていない．本書は**シナリオに依存しない部分**（画面の流れ・モジュール構成・受け渡すデータ・シナリオの書き方）を先に決め，シナリオはデータとして後から差し替えられるようにする．#9 で決まったら書き足す部分は「未決事項」にまとめる．

## 画面の流れ (Screen Flow)

```text
開始画面 (start) ──許可──▶ ホーム (home) ──スタート──▶ ロビー (lobby) ──キャリブレーション完了──▶ シナリオ (scenario) ──終了──▶ 結果 (debrief)
                             ▲                            ▲                                                                  │
                             │                            └──────────────── もう一度（ロビーから） ──────────────────────────┤
                             └───────────────────────────────── ホームへ ───────────────────────────────────────────────────┘
```

| 画面 | ID | 内容 | 次へ進む条件 |
| --- | --- | --- | --- |
| 開始画面 | `start` | 起動直後に 1 回だけ出す許可の画面．周囲 1〜2 m の安全確認の案内．ボタン 1 つで，センサー（`DeviceMotionEvent.requestPermission()`）・カメラ（`getUserMedia`）・音（`AudioContext` の再開と音声の読み込み）の許可をまとめて取る | ボタンをタップし，必要な許可がそろった．カメラが拒否された・使えない時は，手を使わずに進む（「再読み込みすれば使える」と案内を 4 秒出してから自動でホームへ．iOS の Safari は一度拒否すると再読み込みまで尋ね直さないため，その場の再試行は出さない）．センサーが拒否された時は進まず，「もう一度試す」「センサーなしで進む」を出す．許可がそろったらホームへ |
| ホーム | `home` | タイトル「防災シミュレータ（仮）」，横向き・ゴーグル装着の案内，「スタート」と「設定」のボタン．設定では，音量（確認用のナレーションと警報・揺れの効果音を流し，本体の音量ボタンで合わせる．アプリ内の音量は変えない），画面の明るさ（見本の帯．自動調節をオフに・中くらいが目安），画面の消灯（Screen Wake Lock で止められているかの表示．使えない時は自動ロックを「なし」にする案内）を確認する．今後，場面選択（#54）・遊び方の説明を置く場所（`HomeSection` で足す） | 「スタート」をタップした．その回の利用で設定を一度も開いていなければ「音量や画面の明るさは大丈夫ですか？」と聞き，「設定を確認する」か「このまま始める」を選ばせる（`src/lobby/homeSettings.ts` の `shouldConfirmStart`）．許可を取り終えた後に `start` へ進むよう頼まれた時は，app がホームに読み替える（許可を取り直さない．`src/lobby/homeFlow.ts`） |
| ロビー | `lobby` | VR 表示の簡単な部屋．開始ボタンでゴーグルを付ける時間を取った後，見え方の調整（左右の画面の中心の十字が 1 つに重なるよう，スマホの位置やレンズの幅を物理的に合わせる）を行い，ナレーションの指示で (1) 正面を数秒見て向きをリセット (2) 立った姿勢を数秒 (3) しゃがんだ姿勢を数秒 (4) 足踏みを数歩，を順に行い `CalibrationProfile` を作る | すべて終わった（各手順に制限時間を設け，時間切れの時は既定値で進めて詰まらないようにする） |
| シナリオ | `scenario` | 部屋（scenes/）の中で，シナリオ定義に沿って場面を進める．体験中は録画（任意）する | シナリオの最後の場面が終わった，または全体の制限時間を過ぎた |
| 結果 | `debrief` | 場面ごとの「できた／時間切れ」と，正しい行動・危険な行動の一覧を HTML で表示する．録画があれば再生し，アップロード（任意）を行う | 「もう一度」でロビーへ（キャリブレーションは保ったまま），「ホームへ」でホームへ |

- 体験中に画面が消えないよう，開始画面・ホームのタップの中で Screen Wake Lock を取り，ロビー・シナリオの間も保つ（別のアプリから戻った時は取り直す．使えない端末では何もしない．`src/lobby/wakeLock.ts`）
- 画面のタッチは開始画面・ホーム・結果画面だけで使う．ゴーグル装着中（ロビー・シナリオ）は体の動きと手だけで進める（PLAN_04「利用機材」）
- 画面の切り替えは `SceneContext.goTo(次の画面の ID)` で app/ に頼む（後述「受け渡すデータ」）
- 横向きが基本．`?app` のどの画面でも，端末が縦向きの時は全面に「スマホを横向きにしてください」を出す（`src/lobby/orientationGuide.ts`）．出ている間，ロビーは開始ボタンの自動開始・各手順の制限時間・基準の取得を止める（シナリオは止めない）
- 頭の向き（`PlayerInput.head`）は input/ の `createInputSource()` から受け取る（#50．`?app` は `device`，`?app&input=mock` は PC 用の `mock`）．正面リセット済みで，キャリブレーションの前は最初に受け取った向き，後は `yawOffset` が正面になる．ロビーは頭の向きを板の追従と視線の判定（板との相対的な向き）にだけ使い，正面は自分で購読した生の端末の向きで測るため，「もう一度」でロビーに戻った時に `yawOffset` を差し引いた向きを渡しても測る値はずれない．lobby/ の仮実装（`headPose.ts`・`headOrientationFeed.ts`）は app/ からは使っていない

### ロビーの流れ (Lobby Flow)

値は `src/lobby/startGate.ts`（`DEFAULT_START_GATE_CONFIG`）と `src/lobby/calibration.ts`（`DEFAULT_CALIBRATION_CONFIG`）にある．

| 段階 | 内容 | 次へ進む条件 | 制限時間 |
| --- | --- | --- | --- |
| 開始ボタン | 目の前に 3D のボタンを出し，ゴーグルを付けて待つよう案内する．待つ間はキャリブレーションの時間を数えず，センサーの値も捨てる | 今は 15 秒で自動で始まる（`startMode: "auto"`）．input/ の手（`PlayerInput.hands`）が揃ったら，手のひらをボタンに 1 秒かざして始める方式（`startMode: "hand"`）に切り替える | ― |
| 見え方の調整 | 左右それぞれの目の画面の中心に十字を出し，1 つに重なってくっきり見えるよう，スマホの位置やゴーグルのレンズの幅を合わせるよう案内する．値は作らない | 時間で進む | 15 秒 |
| 導入 | これから行う手順を案内する | 時間で進む | 4 秒 |
| 正面 | 正面を向いて止まる → `yawOffset` | 3 秒の間ずれが ±15° 以内 | 8 秒 |
| 立つ | 立って止まる → `standingBaseline` | 最初の 1 秒を捨て，続く 3 秒の揺れが小さい | 8 秒 |
| しゃがむ | しゃがんで止まる → `crouchThreshold` | 基準から十分ずれた後に止まる | 10 秒 |
| 足踏み | その場で足踏み → `stepPeakThreshold` | 6 歩分の山を数える | 12 秒 |
| 終わり | 完了を伝え，`Session.calibration` に書いてシナリオへ | 時間で進む | 3 秒 |

- 時間切れの時は，その手順で取れたデータがあればその値を使い，無ければ既定値（「もう一度」の時は前回の値）のまま次へ進む
- 「もう一度」でロビーに戻った時は，開始ボタン → 見え方の調整 → 導入 → 正面だけを行い，姿勢と足踏みの値は前回のまま保つ（ゴーグルの付け直しで正面がずれるため）
- 各値の意味は暫定で，input/ の判定方法に合わせて担当C・D で決める（「未決事項」）

### 起動の切り替え (Launch Parameters)

| URL パラメータ | 内容 |
| --- | --- |
| （なし）／`?scene=<空間の id>` | PC 確認用の空間ビューア（ドラッグで視点を回す） |
| `?app` | 体験の流れ（開始画面 → ホーム → ロビー → シナリオ）を起動する．入力は実機のセンサー（`createInputSource({ kind: "device" })`）で，頭の向き・足踏み・しゃがみが流れに届く．ロビーのキャリブレーションが終わると `Session.calibration` を入力に渡し，正面を `yawOffset` にリセットする（しきい値は lobby/ と input/ で意味がそろうまで渡さず，入力の既定値を使う．Issue #58）．シナリオは今は仮表示（`Session.calibration` の JSON・`PlayerInput` の中身・「もう一度」「ホームへ」） |
| `?app&input=mock`／`?app&input=device` | 体験の流れの入力を切り替える（`?input=` の解釈は `src/input/inputParam.ts`．指定なしは `device`）．`mock` は PC 用で，キーボードとドラッグで同じ流れを通す（キャリブレーションの後は今の向きを正面にする）．`?app&input=replay` は開発サーバーでだけ，記録した実機の動き（`logs/input/`）を流す（[ENV_04](../02_ENV/ENV_04_開発コマンド.md)） |
| `?stereo=1`／`?stereo=0` | 左右 2 画面の表示を強制する．付けなければスマホ（`(pointer: coarse)` の端末）だけ 2 画面 |
| `?debug` | デバッグ用．ロビーで開始ボタンを 3 秒見つめて始める（横向きで端末がほぼ水平の時だけ数える），Enter／Space で今の段階を飛ばす．本番の経路では使わない |

- 開発の最初に，`input/`・`scenes/`・`lobby/` 等の各フォルダは担当者が自分の PR で作る（今は `core/` と `scenario/` だけがある）

### 依存の向き (Dependency Rules)

```text
                 ┌──────────── app/ ────────────┐
                 │  （すべてを import してつなぐ）  │
                 ▼        ▼        ▼        ▼     ▼
              input/   scenes/  lobby/  scenario/  render/ audio/ recording/ debrief/
                 │        │        │        │        │
                 └────────┴────────┴────────┴────────┴──▶ core/
```

- 各モジュールは `core/` だけを import する．**モジュール同士は直接 import しない**．つなぐのは `app/` だけ
- `input/` は three.js のシーンを import しない（`PlayerInput` は素のデータ．`core/types.ts` の `Vec3`・`Quat` を使う）
- `scenes/` はセンサー・カメラの API（`DeviceMotionEvent`・`getUserMedia` 等）に触れない．入力は `FrameInfo.input` だけから受け取る
- `scenario/` は three.js にもブラウザ API にも依存しない（純粋な TypeScript）．部屋の形は知らず，エリアと物の ID だけを扱う
- `core/` のうち three.js の型を使うのは `core/scene.ts` だけ（型だけの import なので実行時の依存は無い）．`input/`・`scenario/` は `core/scene.ts` を import しない

### 毎フレームの処理 (Frame Loop)

`app/` が以下の順に呼ぶ．

1. `input/` から今の `PlayerInput` を取る
2. 今の画面の `Scene.update({ dt, input })` を呼ぶ（部屋はプレイヤーを動かし，触れた物・出入りしたエリアを `GameEvent` としてイベントバスに流す）
3. シナリオの画面では，このフレームに流れた `GameEvent` と `ScenarioWorld.observe()` から `ScenarioInput` を作り，`advance()` を呼ぶ．返ってきた `effects` をイベントバスへ流す（`Cue` は `scenes/`・`audio/` が受け取る）
4. `render/` で左右 2 画面を描画する

## 処理速度 (Performance)

PLAN_04 の非機能要件「iPhone で 30 fps 以上」を守るため，処理速度の責任を次のように分ける．

### 責任の分担 (Responsibilities)

| 対象 | 責任を持つ人 | 内容 |
| --- | --- | --- |
| 各モジュールの処理時間 | そのモジュールの担当 | 自分のモジュールの処理時間が下記の予算内に収まっているかを，dev ページと実機で自分で確かめる（例: 担当D は入力判定とハンドトラッキングの処理時間） |
| 全体の fps | `render/` の担当 | 実機で全体の fps を見張り，30 fps を下回ったら計測の結果から予算を超えたモジュールを見つけて担当に伝える．予算の割り振りの見直しもまとめる |

### 処理時間の予算 (Time Budget)

30 fps のとき 1 フレームは約 33 ms．これを以下のように割り振る．

**数値は目安である**．Day 1 の実機検証（[ENV_01](../02_ENV/ENV_01_技術スタック.md)「最初に検証すること」）で実測し，見直す．

| モジュール | 処理 | 予算（1 フレームあたり） | 備考 |
| --- | --- | --- | --- |
| `input/` | 足踏み・しゃがみ・頭の向きの判定 | 1 ms | 純粋な関数の計算だけなので小さい |
| `input/` | ハンドトラッキング | 平均 8 ms（認識 1 回あたり 10〜25 ms） | 認識は 10〜15 回/秒（2〜3 フレームに 1 回）に間引き，間のフレームは One Euro フィルタ＋短い外挿でなめらかにする（ENV_01「ハンドトラッキング」）．認識は Worker で動かし，メインスレッドを塞がない（下記） |
| `scenes/` | 部屋の更新（移動・衝突・床の高さ・触れた判定・炎や煙の演出） | 4 ms | 炎・煙のパーティクルは数を絞る |
| `scenario/` | `advance()` | 0.5 ms | 条件の評価だけなので小さい |
| `audio/` | 再生の指示・音源の位置の更新 | 1 ms | 音の処理自体はブラウザが別のスレッドで行う |
| `recording/` | 録画 | 2 ms | 圧縮はブラウザが行うが，描画の読み出しの負荷がかかる．録画あり／なしの fps の差も測る |
| `render/` | 左右 2 画面の描画 | 12 ms | 2 回描画するため最も大きく取る |
| ― | 余裕（ブラウザの処理・ガベージコレクション等） | 約 5 ms | ― |

ハンドトラッキングでメインスレッドを塞がない工夫（`src/input/hand/`．Issue #51 で実装．iPhone での比べ方と結果は Day 1 の実機で確かめる）．

- **Worker 化（既定）**: `HandLandmarker` を Web Worker で動かし，カメラの映像は縮小した `ImageBitmap` にして転送する．処理中の認識は 1 つまでとし，認識中に届いた映像は捨てる（遅れを溜めない）．認識中もメインスレッドは描画を続けられる
- **非同期化（Worker が使えない時）**: メインスレッドで，描画のフレームの外（`setTimeout`）で認識し，結果が届いたフレームから使う（遅れは外挿で隠す）
- **縮小と間引きの調整**: 映像は `320x240` から．全体の fps が 30 を下回ったら認識の頻度を 15 → 10 → 7 回/秒と下げ，戻す時はゆっくり上げる

### 計測のしくみ (Measurement)

- `app/` が毎フレーム，各モジュールの処理（入力の取得・`Scene.update`・`advance`・描画等）の前後を `performance.now()` で測る
- モジュールごとの処理時間（ms．平均と最大）と fps を，**開発時だけ**画面の隅に表示し，実機のログ（ENV_01「実機のログの確認」）にも一定間隔で出す．ゴーグルを付けたままでもログで確かめられる
- 各担当の dev ページでも同じ計測のしくみを使い，自分のモジュールの処理時間を確かめられるようにする
- 本番（GitHub Pages）では計測のしくみを読み込まない

## 判定の安定性 (Stability)

足踏み・しゃがみ・ハンドトラッキングの判定が，ゴーグルを付けた状態で誤判定せず安定して動くことに，`input/` の担当D が責任を持つ．しきい値と判定の処理の調整は担当D が行う．

### 指標の目安 (Metrics)

**数値は目安である**．Day 1 以降の実機検証で実測し，見直す．

| 指標 | 内容 | 目安 |
| --- | --- | --- |
| 誤検出 | 立っているだけ・頭を振っただけで，歩行やしゃがみと判定される | 30 秒立って周りを見回す間に 0 回 |
| 見逃し | 足踏み・しゃがみをしたのに判定されない | 10 回のうち 9 回以上判定される |
| 判定の遅れ | 動作を始めてから視点が動く（前進する・下がる）まで | 足踏みは 0.5 秒以内，しゃがみは 1 秒以内 |
| 手の位置のぶれ・途切れ | 手を止めているのに表示が震える，かざしているのに見失う | 止めた手の表示が目で見て震えない．かざしている間の見失いは 1 秒以内に戻る |
| 時間経過でのずれ（ドリフト） | 体験の後半に正面の向きや立ち／しゃがみの基準がずれる | 3 分の体験の終わりでも，正面のずれと姿勢の誤判定が目立たない |
| 人・端末の違いへの強さ | 背の高さ・動きの大きさ・端末が違っても同じように判定される | キャリブレーションの後，メンバー全員とデモ用の iPhone で上記を満たす |

### 確かめ方 (Verification)

- **記録データでの再現テスト**: 開発用ページで記録したセンサーの CSV と判定ログを入力にして，判定の純粋な関数を Vitest でテストする．誤判定が起きた記録はテストに足し，しきい値を変えても再発しないようにする
- **ゴーグルを付けた実機での確認**: 決まった動作を決まった回数行い，成否を数える．例:
  1. 立ったまま頭を左右・上下に振る（30 秒）→ 歩行・しゃがみと判定されないこと
  1. その場で足踏みを 10 歩 × 3 回 → 前進すること，止めたら止まること
  1. しゃがんで立つを 10 回 → 毎回切り替わること
  1. 手を正面にかざして止める・動かす → 表示が追従し，ぶれないこと
- **複数のメンバーで試す**: 背の高さや動き方の違う複数のメンバーで同じ手順を行い，人による違いを確かめる

## シナリオ定義の形式 (Scenario Definition Format)

シナリオは `ScenarioDefinition`（`src/scenario/types.ts`）として**データだけで**書く．進行エンジン（`src/scenario/engine.ts`）はシナリオの中身を知らず，どの災害のシナリオでも同じエンジンで動く．

### 場面 (Step)

シナリオは場面（step）の配列で，先頭の場面から始まる．各場面には次を書く．

| 項目 | キー | 内容 |
| --- | --- | --- |
| 開始時の演出 | `onEnter` | 場面に入った時の `Cue` の列（ナレーション ID・効果音 ID・発生させる出来事） |
| 求める動作 | `goal` | 判定条件（後述）．満たしたら次の場面へ進む |
| できた時の演出 | `onComplete` | 求める動作ができた時の `Cue` の列（「よくできました」等） |
| 制限時間 | `timeout` | 秒数・時間切れの時の演出・時間切れの時の行き先（省略時は次の場面）．**詰まらないよう，時間切れでも先へ進めるのを基本にする** |
| 助言 | `hints` | 場面に入ってから一定秒数たった時に出す `Cue`（「机の下にもぐりましょう」等） |
| 行動の評価 | `checks` | 場面の途中で検出する正しい行動・危険な行動．条件を満たしたら 1 回だけ記録し，結果画面に出す |
| 結果画面の見出し | `report` | この場面で求めた動作の説明と助言．省略した場面（導入・締めのナレーション等）は結果画面に出さない |
| 次の場面 | `next` | 次の場面の ID．省略時は配列の次の場面，`null` で終了 |

- シナリオ全体にも制限時間（`timeLimitSeconds`）を付けられる．過ぎたら打ち切って結果画面へ進む（PLAN_04「体験時間」の 2〜3 分を守るため）
- 場面の制限時間・全体の制限時間は，正の有限な数でなければならない（0 以下・`NaN`・`Infinity` は `validateScenario` が誤りとして返す）

### 進め方の規則 (Progression Rules)

- 1 回の `advance()`（1 フレーム）で切り替わる場面は 1 つまで．新しい場面の条件は次のフレームから評価する
- 1 フレームの中では，助言 → 行動の評価（`checks`）→ 求める動作（`goal`）→ 時間切れの順に判定する
- **達成は時間切れより優先する**．同じフレームで次が重なった時は，達成として扱う
  - 求める動作の達成と，場面の制限時間の超過 → その場面は `completed`
  - 求める動作の達成と，全体の制限時間の超過 → その場面は `completed`．それが最後の場面（行き先が `null`）なら通常の終了とし，打ち切り（`aborted`）にしない．まだ場面が残っていれば，そこで打ち切る（`aborted: true`）
  - 場面の時間切れと全体の制限時間の超過が重なった時も同じく，行き先が残っていなければ通常の終了，残っていれば打ち切りとする
- **出来事の持ち越し**: 場面が切り替わったフレームに届いた出来事（`objectTouched`・`signal`・`areaEntered` 等）のうち，前の場面で**使われなかった**ものは状態（`pendingEvents`）に持ち越し，次の `advance()` で新しい場面の条件の評価に使う（そのフレームの出来事より前に並べる）．エンジンは純粋な関数のままで，持ち越しも状態として返す
  - 「使われた」とは，前の場面の求める動作（`goal`）または行動の評価（`checks`）の判定で，`touch`・`signal` の条件に一致した出来事をいう（その条件がすでに満たしたまま（ラッチ）で判定されなかった場合は使われていない）
  - これにより，1 回の接触で 2 つの場面が続けて達成されることを防ぎつつ，場面の切り替えと同時に届いた別の出来事（例: ナレーションの終わり）は取りこぼさない
  - 持ち越すのは 1 回の切り替えにつき 1 フレーム分だけで，次のフレームで評価した後は捨てる（さらに場面が切り替われば，同じ規則でまた持ち越す）

### 判定条件 (Conditions)

判定条件は `type` で区別する union（`Condition`）．新しい種類が要る時は型に 1 つ足し，エンジンの `evaluateLeaf` に分岐を 1 つ足す．

| `type` | 意味 | 例 |
| --- | --- | --- |
| `posture` | 指定の姿勢を `holdSeconds` 秒続けた | しゃがみを 3 秒続けた |
| `walking` | 足踏みを `holdSeconds` 秒続けた | 揺れの最中に 3 秒歩いた（危険な行動） |
| `inArea` | 指定のエリアに `holdSeconds` 秒いた | 机の下・廊下・屋外の集合場所に着いた |
| `touch` | 指定の物に手で触れた | ドア・消火器・非常ベルに触れた |
| `signal` | 部屋や音響から指定の出来事が届いた | ドアが開いた・ナレーションが終わった |
| `elapsed` | 場面に入ってから一定秒数たった | ナレーションを聞かせるだけの場面 |
| `all`／`any` | 複数の条件のそれぞれを一度は満たした／どれかを満たした（同時でなくてよい） | ドアに触れた，かつ廊下に着いた（順番・時刻は問わない） |
| `together` | 複数の条件を**同時に**満たしている状態が `holdSeconds` 秒続いた（途切れたら 0 秒に戻る） | 机の下のエリアで，しゃがんだ状態を 3 秒続けた |

- 一度満たした条件は，その場面の間は満たしたままとして扱う（ラッチ）．`together` も，一度成立したらその場面の間は満たしたままになる
- エリアの形・物の位置はシナリオに書かない．シナリオは ID だけを書き，形と位置は `scenes/` の部屋が決める（同じシナリオを別の部屋に載せ替えられる）

#### all と together の違い (All vs Together)

`all` は子の条件をそれぞれラッチするため，「場面の中でそれぞれ一度は満たした」の意味になる．`together` は子をラッチせず，「今この瞬間すべてを満たしているか」を毎フレーム見る．

例として「机の下のエリアにいる」と「しゃがんでいる」を組み合わせ，体験者が「机の下に入る → 机の外に出る → しゃがむ」と動いた場合:

| 書き方 | 結果 |
| --- | --- |
| `all`: `inArea`（`under-desk`）と `posture`（`crouching`，`holdSeconds: 3`） | 成立する（机の下にいたこと，しゃがみを 3 秒続けたことが，別々の時に一度ずつあればよい） |
| `together`: `inArea`（`under-desk`）と `posture`（`crouching`），`holdSeconds: 3` | 成立しない（机の下で，しゃがんだ状態が同時に 3 秒続く必要がある） |

「その場所でその姿勢をとる」のように**同時であることに意味がある**条件は `together` で書く．

#### together の子の評価 (Children of Together)

`together` の子は，ラッチを使わず「今この瞬間満たしているか」で評価する．

| 子の種類 | 「今満たしている」の意味 |
| --- | --- |
| `posture`・`walking`・`inArea` | 今その状態である．子に `holdSeconds` があれば，その子自身の継続時間（途切れたら 0 に戻る）を今満たしていること |
| `touch`・`signal` | **そのフレームに**一致する出来事が届いた時だけ満たす（瞬間的な出来事のため，次のフレームには満たさなくなる）．`holdSeconds` を付けた `together` の子にすると，ほぼ成立しなくなるので避ける |
| `elapsed` | 場面に入ってから指定の秒数を過ぎている |
| `all`／`any` | 子を今の状態で評価した，すべて／どれか（`together` の中ではラッチしない） |
| `together` | 入れ子の `together` は自身の継続時間を数え，今それを満たしているか（ラッチしない） |

### 進行エンジン (Engine)

エンジンは純粋な関数で，同じ入力には同じ結果を返す．センサーの記録や手で作った入力の列で単体テストできる．

| 関数 | 内容 |
| --- | --- |
| `startScenario(定義)` | 最初の場面に入った状態と，その演出を返す |
| `advance(定義, 状態, 入力, このフレームの出来事, dt)` | 1 フレーム進めた状態と，出す通知（`effects`: 演出・場面の開始／終了・評価・終了）を返す |
| `toResult(定義, 状態)` | 結果画面・アップロード用の `ScenarioResult` にまとめる |
| `validateScenario(定義)` | ID の重複・存在しない行き先・正の有限な数でない制限時間等の誤りを返す |

### 書き方の例（サンプル）(Sample)

**以下は書き方を示すためのサンプルであり，確定したシナリオではない**（#9 で決まったら差し替える）．全文は `src/scenario/samples/earthquake-fire-evacuation.ts` にある．PLAN_04 の候補「地震→火災→避難」を例にした．

| 場面 | 開始時の演出 | 求める動作 | 制限時間・時間切れ | 評価 |
| --- | --- | --- | --- | --- |
| `intro` | 環境音，導入のナレーション | ナレーションが終わる（または 8 秒） | ― | ― |

| `open-door` | 「ドアを開けて」のナレーション | ドアに手で触れる | 20 秒（8 秒で助言） | ― |
| `evacuate` | 「外へ出よう」のナレーション | 集合場所のエリアに 1 秒いる | 30 秒 | ― |
| `ending` | 音を止めて締めのナレーション | 5 秒たつ | ― | ― |

### 他の候補も同じ形式で書けること (Other Scenarios)

PLAN_04 のシナリオ候補は，どれも同じ判定条件の組み合わせで書ける．

| 候補 | 書き方の例 |
| --- | --- |
| 地震のみ | `together`（落下物の無い場所でしゃがみを続ける）・`walking` を危険な行動として `checks` に |
| 火災のみ | `touch`（消火器）→ `signal`（消火できた，は部屋が判定して送る）→ `inArea`（出口）．煙の中の姿勢は `checks` に |
| 水害・津波避難 | `inArea` を順に並べる（高台・避難ビル）．全体の制限時間で切迫感を出す |

## 開発時の独立性 (Independent Development)

各担当が他の担当の完成を待たずに開発できるよう，以下を用意する．

- **モック入力**: キーボードとマウスで `PlayerInput` を作る（W／S で歩行，C でしゃがみの切り替え，左ドラッグで頭の向き，マウスの位置で右手の位置，右ボタンか F キーを押している間は握る，ホイールで手の奥行き）．PC のブラウザだけで部屋とシナリオを確かめられる．置き場所は `src/input/`（担当D）とし，`app/` で本物の入力と切り替える
- **各自の dev ページ**: 担当ごとに単独で動かせるページを作る（例: input/ はセンサーの値と判定結果を表示し CSV で書き出すページ，scenes/ はモック入力で部屋を歩くページ，scenario/ はシナリオの進行を文字で表示するページ）．本番のビルドには含めない
- **API はモックから**: アップロードはブラウザ側のモック（受け取った内容をログに出すだけ）で作り始め，サーバーができたら差し替える
- **シナリオはサンプルから**: 部屋と音響はサンプルのシナリオの ID で作り始め，#9 で確定したら ID を合わせる

## バックエンド (Backend)

- [ENV_01](../02_ENV/ENV_01_技術スタック.md)「方針」の「サーバーは持たない．静的サイトとして配信し，体験中は通信無しで動かす」は**維持する**．体験（開始画面〜結果画面）は静的サイトだけで完結し，体験中は通信しない
- `server/` は**体験の後のアップロード専用の任意機能**とする（録画・行動の記録の送信．[PLAN_05](../03_PLAN/PLAN_05_追加機能の候補.md) の「AI による振り返り」「体験の録画と振り返り再生」の土台）
- 送れなくても体験は完結する．送信に失敗した時は，端末に保存する（ダウンロード）か，再送できるようにする
- ブラウザとサーバーで共有する型（送る内容・応答）は `shared/api.ts` に置く
- ENV_01 は現在「サーバーは持たない」とだけ書いている．アップロード用のサーバーを実際に置く場合の書き方（配信先・費用・API キーの扱い）は「未決事項」とする
