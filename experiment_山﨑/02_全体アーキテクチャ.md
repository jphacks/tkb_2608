# 全体アーキテクチャ (Architecture)

`input/` の処理の流れ・スレッドの構成・遅延の予算を定める．

## 処理の駆動 (Event-Driven Processing)

センサーの値は，描画のフレームとは別の周期で届く（iOS の `devicemotion` は約 60 Hz，Android ではより速いことがある）．フレームごとにまとめて処理すると，届いた値の数がフレームによって 0〜3 個とばらつき，判定がぶれる．

- **決定**: センサーのイベントが届くたびに，判定の状態を O(1) で 1 サンプル分進める．描画のループ（`requestAnimationFrame`）は，最新の状態を読んで `PlayerInput` を組み立てるだけにする
- 時刻はイベントの `timeStamp`（`performance.now()` と同じ基準）を使い，サンプルの間隔から `dt` を求める．周期が端末ごとに違っても，フィルタの係数を `dt` に合わせることで同じように判定できる
- フレームが落ちてもセンサーの処理は止まらないため，判定の精度が描画の重さに左右されない

```text
devicemotion（約 60 Hz）──▶ motion の純粋関数 ──▶ 歩き・姿勢の状態
deviceorientation      ──▶ 頭の向きの状態
                                                         │
カメラ（約 30 fps）──▶ Worker: HandLandmarker（10〜15 回/秒）──▶ 手の状態
                                                         │
requestAnimationFrame ──▶ 最新の状態を読む ──▶ PlayerInput ──▶ app/
                          └ 頭の向きはここで先読みして描画の直前に渡す
```

## 純粋な関数と薄い殻 (Pure Core, Thin Shell)

| 層 | 内容 | テスト |
| --- | --- | --- |
| 純粋な関数 | `stepMotion(state, sample, params) → state` のように，状態とサンプルから次の状態を返す．ブラウザ API に触れない | 記録した CSV／JSONL を流し込んで Vitest でテストする |
| 殻 | `addEventListener`・`getUserMedia`・Worker とのやり取り．値を純粋な関数に渡すだけ | 実機と dev ページで確かめる |

- 同じ入力から必ず同じ結果が出るため，実機で起きた誤判定を PC で再現できる（[10](10_デバッグ環境と動きの記録.md)）
- しきい値は `params` として外から渡す．dev ページからその場で変えられ，記録の再生でも変えて比べられる

## 出力の形 (Output Shape)

判定の結果は，独立した 3 つの部分に分ける．

| 部分 | 中身 | `PlayerInput` の項目 |
| --- | --- | --- |
| 頭 | 向き（正面リセット済み） | `head` |
| 体 | **姿勢（立つ／しゃがむ）× 移動（歩く／止まる）** の 2 つの軸．4 つの組み合わせのすべてを表せる | `posture`・`walking`・`walkSpeed` |
| 手 | 左右それぞれの認識の有無・位置・形 | `hands` |

- 姿勢と移動を 1 つの状態にまとめないことで，しゃがみ歩きを自然に表せる（[05](05_しゃがみ_立ち上がり_しゃがみ歩き.md)）
- 今の `PlayerInput` の型で表せる．手の形（つまむ・指を差す）を足す時だけ `HandState` を広げる（[07](07_ハンドトラッキングと手の動作.md)）

## スレッドの構成 (Threads)

| スレッド | 処理 |
| --- | --- |
| メイン | センサーの購読と判定（1 サンプルあたり数 µs），`PlayerInput` の組み立て，描画 |
| Worker | `HandLandmarker` の認識（1 回 10〜25 ms）．カメラの映像は `ImageBitmap` にして転送する |

- 手の認識だけを別のスレッドに出すことで，認識するフレームだけ重くなってフレームが落ちる問題を避ける
- Worker で動かない場合は，メインスレッドで非同期に動かす（[07](07_ハンドトラッキングと手の動作.md)）

## 遅延の予算 (Latency Budget)

### 頭の向き (Head Rotation)

酔いに最も直結するため，最も厳しく抑える．

| 区間 | 目安 | 工夫 |
| --- | --- | --- |
| センサーの計測 → イベントが届く | 約 10〜17 ms | ― |
| イベント → 描画に使われる | 0〜16 ms | 描画の直前に最新の値を読む |
| 描画 → 画面に出る | 約 16〜33 ms | ― |
| 合計 | 約 30〜60 ms | ジャイロで約 30 ms 先読みし，**体感の遅れを 1 フレーム以下にする**（[03](03_頭の向きと見回し.md)） |

### 体と手 (Body & Hands)

| 判定 | SPEC の目安 | 狙い | 内訳 |
| --- | --- | --- | --- |
| 足踏みの動き出し | 0.5 秒以内 | 0.3〜0.4 秒 | 1 歩目の山（足を着いた衝撃）を待つ時間．1 歩目で低速で仮に動き出す（[04](04_足踏み.md)） |
| 足踏みの止まり | ― | 0.5〜0.8 秒 | 歩く周期の 1.5 倍の間に山が無ければ止める |
| しゃがみ・立ち上がり | 1 秒以内 | 0.6〜0.9 秒 | 動作そのもの（0.5〜1 秒）が終わった時点で確定する．目の高さは動作の途中から追い始める |
| 手の位置 | ― | 約 20〜40 ms | 認識の時間＋転送．外挿で次の結果までの間を埋める（[07](07_ハンドトラッキングと手の動作.md)） |
