# テスト方針 (Testing Policy)

アプリのテスト（Vitest）を書くとき・テストの対象になるコードを書くときは本ルールに従うこと．本ルールは，すでにマージされたテストの書き方を明文化したものである（Issue #39）．
実行コマンドは [ENV_04](../../docs/02_ENV/ENV_04_開発コマンド.md)（`npm test`）．PR では CI が実行し，合格しないとマージできない．

## 何をテストするか (What to Test)

| 対象 | テスト | 例 |
| --- | --- | --- |
| 判定・計算の純粋な関数 | **必ず書く**．境界値と異常値（`NaN`・`null`・範囲外）を含める | 入力の正規化，足踏み・しゃがみの判定，シナリオ進行エンジン，配置の計算 |
| シナリオ定義（データ） | 必ず書く．定義の整合性（参照する ID・エリアが存在する等）と，代表的な進み方を確かめる | `scenario/samples/*.test.ts` |
| 3D の空間の組み立て | 書く．物の数・名前・位置・`userData` 等の**構造**を確かめる．描画結果（ピクセル）は見ない | `scenes/room/room.test.ts` |
| ブラウザ API の薄い殻 | 書かなくてよい（実機で確かめる）．殻を薄く保ち，判定を純粋な関数に出すことでテストの対象を増やす | センサーの購読・カメラの起動 |
| 見た目・操作感・実機の挙動 | テストでは確かめない．人間が実機で確かめる（CLAUDE.md「手動確認が必要な作業」） | 揺れの強さ，酔いにくさ |

- 不具合を直すときは，先に不具合を再現するテストを書いて失敗を確かめてから直す
- テストを通すためにテストを弱めない（期待値を実装に合わせて書き換えない）．仕様のほうが変わった場合は，その理由を PR に書く

## 置き場所と名前 (Location & Naming)

- テストは対象と同じフォルダに `<対象>.test.ts` として置く（Vitest の対象は `src/**/*.test.ts`）
- `scripts/` の `.mjs` のテストも，`src/scripts/<名前>.test.ts` に置く（Vitest の対象が `src/` のため．例: `src/scripts/tunnel.test.ts`）
- `describe` には対象の関数・型の名前を，`it` には**期待する振る舞いを日本語で**書く（例: `it("有限の数はそのまま")`）

## 書き方 (How to Write)

- 入力の組み合わせが多いものは `it.each` で表にする
- テスト用のデータは，既定値を持ち一部だけ上書きできる作成関数にする（例: `motion({ interval: 0 })`）．テストごとに大きなオブジェクトを書き写さない
- テストは node 環境で動く（DOM は無い）．three.js の組み立てで canvas 等が要る場合は，テストの中で最小限の代わり（何もしない canvas 等）に差し替え，`afterAll` で元に戻す（例: `scenes/room/room.test.ts`）
- 時刻・乱数・ネットワークに依存させない．時刻は引数で渡すか `vi.useFakeTimers()` を使い，乱数は種付きの乱数を渡す．外部への通信はしない
- 作った three.js のオブジェクトは，テストの最後に `dispose()` する

## センサーの記録データ (Sensor Recordings)

- 足踏み・しゃがみ等の判定は，開発用ページ（`src/input/dev/`）で実機から記録したデータでテストする（SPEC_01「判定の安定性」）
- テストに使う記録は，必要な区間だけを小さく切り出し，対象と同じフォルダの `fixtures/` に置く（大きな記録をそのままコミットしない．`logs/` は `.gitignore` 済みで，記録の元データはそこに置く）
- 記録には，どの端末・装着状態・動作（例: 「iPhone・ゴーグル装着・その場で足踏み 10 歩」）かをファイル名かコメントで残す
